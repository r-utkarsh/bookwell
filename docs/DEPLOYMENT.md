# Deployment

Bookwell is a monorepo with a Spring Boot API in `backend/` and a Vite SPA in
`frontend/`. The deployment target is Render (Docker web service + Render
PostgreSQL) and Vercel (static frontend), with GitHub Actions providing CI.

The repository contains `render.yaml`, `backend/Dockerfile`,
`frontend/vercel.json`, and `.github/workflows/ci.yml`. No production secrets are
committed.

> Deployment was **not** performed as part of this project. These are verified
> configuration instructions, not a claim that a live environment exists.

## 1. Prerequisites

- A GitHub repository containing this project.
- A Render account and workspace.
- A Vercel account.
- An SMTP provider. Production startup intentionally fails unless
  `MAIL_MODE=smtp`, `MAIL_HOST`, and `MAIL_FROM` are set.
- A strong bootstrap administrator password: 10–72 printable characters,
  containing a letter and a number, with no spaces.

## 2. Backend and PostgreSQL on Render

### Option A: Blueprint (recommended)

1. Push the repository to GitHub.
2. In Render, choose **New → Blueprint** and select the repository.
3. Render reads `render.yaml` and proposes:
   - `bookwell-api` — Docker web service, health check `/actuator/health`
   - `bookwell-db` — PostgreSQL database
4. Fill every `sync: false` variable when prompted:

   | Variable | Example / guidance |
   |---|---|
   | `CORS_ALLOWED_ORIGINS` | `https://bookwell.vercel.app` (exact origin, no trailing slash) |
   | `APP_PUBLIC_URL` | `https://bookwell.vercel.app` (HTTPS, used in email links) |
   | `MAIL_HOST` | `smtp.your-provider.com` |
   | `MAIL_USERNAME` | SMTP username |
   | `MAIL_PASSWORD` | SMTP password or app password |
   | `MAIL_FROM` | `no-reply@your-domain.com` |
   | `BOOTSTRAP_ADMIN_EMAIL` | Your administrator email |
   | `BOOTSTRAP_ADMIN_PASSWORD` | Strong one-time password |

   `MAIL_PORT=587`, STARTTLS, authentication, and `MAIL_FROM_NAME` are already
   set in the Blueprint. `JWT_SECRET` is generated by Render as a 256-bit
   Base64 value.
5. Apply the Blueprint and wait for the first deploy. Flyway applies
   `V1__initial_schema.sql` automatically on startup; Hibernate only validates
   the schema.
6. Verify:
   - `https://<service>.onrender.com/actuator/health` returns `{"status":"UP"}`.
   - `https://<service>.onrender.com/swagger-ui.html` loads.
   - The Render logs contain `Production configuration validation passed.` and
     no Flyway errors.
7. Sign in as the bootstrap administrator, then **remove**
   `BOOTSTRAP_ADMIN_EMAIL` and `BOOTSTRAP_ADMIN_PASSWORD` from the Render
   environment. The runner only creates the account if it does not exist, but
   removing the values prevents accidental reuse.

### Option B: Manual service

If you do not use the Blueprint:

1. Create a Render PostgreSQL instance. Note its **internal connection string**
   (`postgresql://user:password@host:5432/database`).
2. Create a **Web Service** from the repository:
   - Runtime: Docker
   - Root directory: `backend`
   - Dockerfile path: `./Dockerfile`
   - Health check path: `/actuator/health`
3. Set the environment variables from the table above plus:

   ```text
   APP_ENV=production
   DB_URL=<internal connection string>
   DB_USERNAME=<database user>
   DB_PASSWORD=<database password>
   AUTH_COOKIE_SECURE=true
   AUTH_COOKIE_SAME_SITE=None
   TRUST_FORWARDED_HEADERS=true
   JWT_SECRET=<openssl rand -base64 48>
   DEFAULT_TIME_ZONE=Asia/Kolkata
   DEFAULT_CURRENCY=INR
   NOTIFICATIONS_ENABLED=true
   NOTIFICATION_WORKER_ENABLED=true
   MAIL_MODE=smtp
   MAIL_PORT=587
   MAIL_STARTTLS=true
   MAIL_AUTH=true
   SEED_ENABLED=false
   RATE_LIMIT_ENABLED=true
   ```

### Hosted database URL handling

Render provides a URI, **not** a JDBC URL:

```text
postgresql://bookwell:password@dpg-xxxx-a/database
```

Spring cannot consume that directly. `DatabaseUrlEnvironmentPostProcessor`
converts `postgres://` and `postgresql://` values into:

```text
jdbc:postgresql://dpg-xxxx-a/database
```

It also URL-decodes the username/password embedded in the URI unless
`DB_USERNAME` / `DB_PASSWORD` are set explicitly. Native `jdbc:postgresql://`
values pass through unchanged. The normalizer is unit-tested and registered via
`META-INF/spring.factories`, which is the file Spring Boot 3.5 loads
`EnvironmentPostProcessor` implementations from.

You can still supply a plain JDBC URL manually if your provider exposes one. Do
not paste a `postgresql://` URI into `spring.datasource.url` directly.

### Production fail-fast behavior

With `APP_ENV=production`, startup fails if any of these are missing or unsafe:

- `JWT_SECRET` (must be Base64 and decode to at least 32 bytes)
- `AUTH_COOKIE_SECURE=true`
- At least one exact CORS origin
- `MAIL_MODE=smtp`, `MAIL_HOST`, `MAIL_FROM`
- `APP_PUBLIC_URL` using HTTPS
- `spring.jpa.hibernate.ddl-auto=validate`
- `SEED_ENABLED=true` (demo seeding is rejected in production)
- `MAIL_HOST=localhost`

This is intentional: a misconfigured deployment should fail visibly instead of
pretending email or authentication is working.

## 3. Frontend on Vercel

1. Import the same GitHub repository into Vercel.
2. Configure the project:
   - **Root Directory**: `frontend`
   - **Framework Preset**: Vite
   - **Build Command**: `npm run build`
   - **Output Directory**: `dist`
   - **Install Command**: `npm ci`
3. Add the environment variable:

   ```text
   VITE_API_BASE_URL=https://<backend-service>.onrender.com
   ```

   This is public configuration, not a secret. It is embedded at build time, so
   redeploy after changing it. Do not put JWT secrets, SMTP credentials, or
   database URLs in any `VITE_*` variable.
4. Deploy. `frontend/vercel.json` rewrites client-side routes to `index.html`
   and adds baseline security headers.
5. Copy the production frontend origin (for example
   `https://bookwell.vercel.app`).
6. In Render, update:
   - `CORS_ALLOWED_ORIGINS` to the exact frontend origin
   - `APP_PUBLIC_URL` to the exact frontend origin
7. Redeploy/restart the backend if Render does not apply the variables
   automatically.

### CORS and cookies

The SPA and API are on different sites, so authentication uses:

- `AUTH_COOKIE_SECURE=true`
- `AUTH_COOKIE_SAME_SITE=None`
- CORS credentials enabled with an exact origin (wildcards are rejected)
- HTTPS on both origins

The refresh cookie is HttpOnly, scoped to `/api/v1/auth`, and cannot be read by
JavaScript. Access tokens live only in memory. If login appears to succeed but
refreshing fails, check:

1. Both sites are HTTPS.
2. `CORS_ALLOWED_ORIGINS` exactly matches the browser origin (scheme + host,
   no path, no trailing slash).
3. `AUTH_COOKIE_SAME_SITE=None` and `AUTH_COOKIE_SECURE=true`.
4. The browser's network panel shows `Set-Cookie: bookwell_refresh` on login.
5. No privacy extension or proxy is stripping `Set-Cookie`.

## 4. Notifications and scheduled work

- Booking confirmations, cancellations, reschedules, and 24-hour reminders are
  persisted in the `notifications` table in the same transaction as the booking
  change.
- A scheduled worker claims due rows with a pessimistic lock, sends outside the
  claim transaction, and retries failures with bounded exponential backoff.
- Delivery is **at-least-once**. A crash after SMTP accepts a message but before
  the database marks it `SENT` can produce a duplicate. Dedupe keys prevent a
  second job for the same logical event, not a duplicate SMTP retry.
- In development, `MAIL_MODE=log` prints the message and marks it `SENT` with
  `delivery_mode=LOG`. This is intentionally rejected in production.
- Render free web services spin down when idle. **Timed reminders are not
  reliable on a sleeping free instance.** Use an always-on paid instance, an
  external scheduler that wakes the service, or accept that reminders may be
  delayed until the next request. Booking confirmation emails still enqueue
  immediately and are delivered when the worker next runs.
- With multiple backend instances, the database claim prevents duplicate
  processing, but each instance schedules its own poll. This is safe; it adds
  no extra sends. The login/registration rate limiter is in-memory per instance
  and is not a distributed limiter.

## 5. Database migrations and operations

- Flyway owns the schema. `spring.jpa.hibernate.ddl-auto=validate`.
- Migrations run on application startup. They are forward-only and must remain
  backward compatible during rolling deploys.
- Do not enable demo seeding in production; the application rejects it.
- Take a Render database backup/snapshot before applying destructive schema
  changes. Review any new migration in CI and on a staging database first.
- The schema requires `btree_gist`; the migration creates it with
  `CREATE EXTENSION IF NOT EXISTS btree_gist`. The database user must be allowed
  to create extensions (the Render owner user is).
- Connection pool defaults to 10; the Blueprint sets `DB_POOL_SIZE=5` for a small
  Render database. Adjust to the provider's connection limit.

## 6. CI and deployment gating

`.github/workflows/ci.yml` runs on pushes and pull requests:

- Backend: Java 21, Maven wrapper, full Testcontainers integration suite.
- Frontend: Node 22, `npm ci`, lint, Vitest, production build.
- Backend test reports are uploaded as an artifact.

`render.yaml` uses `autoDeployTrigger: checksPass`, so Render only deploys a
commit after its GitHub checks pass. The workflow runs on pushes to `main` and
on pull requests. Keep `main` as the repository's default branch, or update the
`branches` list in `.github/workflows/ci.yml`; otherwise pushes to another
default branch will not produce the checks Render waits for.

Render's free web and PostgreSQL plans have usage and expiry limits. Use a paid
plan for a long-lived production deployment.

## 7. Alternative static hosting

The frontend is a standard Vite SPA. Any static host that supports SPA fallback
works:

- Build: `npm ci && npm run build`
- Publish: `frontend/dist`
- Set `VITE_API_BASE_URL` at build time.
- Rewrite unknown paths to `/index.html`.
- Keep the same HTTPS/CORS/cookie requirements.

## 8. Post-deployment checklist

- [ ] `GET /actuator/health` is UP.
- [ ] Flyway migration completed and `flyway_schema_history` has V1.
- [ ] Administrator can sign in with the bootstrap account.
- [ ] Bootstrap admin credentials removed from Render.
- [ ] Provider application → admin approval → public listing works.
- [ ] Customer registration, discovery, availability, and booking work.
- [ ] Browser network panel shows HttpOnly refresh cookie and no tokens in
      localStorage/sessionStorage.
- [ ] Two simultaneous booking attempts produce one success and one
      `409 SLOT_UNAVAILABLE` (test on staging; the automated proof is
      `BookingConcurrencyIT`).
- [ ] Confirmation email is delivered, or the outbox shows a clear failure.
- [ ] Reminder worker behavior matches the chosen Render plan.
- [ ] CORS preflight from the Vercel origin succeeds.
- [ ] Frontend deep links such as `/providers/<id>` reload correctly.

## 9. Rollback

- Render keeps deploy history; roll back the web service to a previous image.
  Database migrations are not automatically rolled back. If a release added a
  migration, either roll forward with a corrective migration or restore from a
  backup.
- Vercel supports instant rollback to a previous deployment. Because
  `VITE_API_BASE_URL` is compiled in, confirm the rolled-back frontend targets
  the intended API.
- Never run `flyway clean` against a production database.
